# JobProof 产品说明计划书

> 用真实问题做出可验证的实习能力证明

## 一、项目概述

JobProof 是面向大学生的实习求职能力转化工具。它把“发现目标岗位—理解岗位要求—补齐能力—产出证据—形成求职表达”串成一条可执行、可复盘的路径。

用户不再只得到一份岗位推荐或一段 AI 生成的建议，而是从目标 JD 出发，完成一个 7 天或 14 天的微项目，留下任务成果、过程证据和可用于简历、作品集及面试的真实表达。

项目当前公网入口：<https://jobproof-mvp.netlify.app>  
项目代码仓库：<https://github.com/MrNucleus/JobProof>

## 二、创作背景与核心问题

大学生在实习求职中常见的困难不是“看不到岗位”，而是无法把岗位描述转化成自己的行动计划：

- 看懂了 JD，却不知道自己究竟缺哪些能力；
- 有课程、社团或零散经历，却没有能被招聘方快速理解的成果证据；
- 想通过项目提升能力，但项目题目脱离真实业务，做完也难以写进简历；
- 看到大量经验分享后仍停留在收藏和焦虑，缺少从阅读到实践的下一步；
- AI 可以生成漂亮的文字，却不能自动证明这些能力确实被用户实践过。

JobProof 要解决的核心断层是：

> 将“岗位要求”和“社区里的真实问题”转化为用户可以在短周期内完成，并能提交证据、复述过程的微项目。

## 三、创作思路

### 1. 从目标岗位开始，而不是从泛泛学习开始

用户先填写或粘贴自己真正想申请的 JD。系统识别岗位职责、能力要求和关键词，再结合用户注册时完成的个人能力确认，给出差距解释。这样学习任务与求职目标绑定，减少无效刷课和盲目准备。

### 2. 从“知道”走向“做过”

系统把能力缺口拆成 7 天或 14 天微项目，每个项目包含任务、交付物、预计用时和验收标准。用户通过实际产出建立证据链，而不是只勾选“我会不会”。

### 3. 用知乎真实讨论提供问题语境

知乎拥有大量围绕职业、行业、产品、运营和技术实践的真实提问与回答。JobProof 在用户选择目标能力后，调用知乎开放能力检索相关讨论，生成 3 个可选主题，并保留原始链接、标题、摘要、作者和获取时间。

知乎内容在产品中承担的是“真实问题来源”和“研究语境”角色，不直接替代用户成果，也不把点赞量或关注关系当作能力证明。

### 4. 让成果可以被验证和复用

用户在项目过程中记录背景、任务、行动、结果和反思，系统检查证据完整度，再生成三种求职表达：简历要点、作品集案例和 STAR 面试故事。每段表达都回链到用户自己的证据，便于复盘和面试追问。

## 四、目标用户与典型场景

### 目标用户

- 正在寻找第一段实习的大一至大四学生；
- 已有目标岗位，但不知道如何补齐 JD 能力要求的学生；
- 有零散经历、缺少完整项目案例的转专业或跨方向求职者；
- 希望把知乎阅读、行业观察转化为作品的学生。

### 典型场景

以“产品运营实习生”为例：用户粘贴目标 JD，系统发现其需要用户调研、竞品分析、数据整理和项目跟进能力；用户从知乎相关讨论中选择“校园产品用户反馈分析”主题，完成调研设计、样本整理、结论输出和复盘，最后得到一份可展示的分析报告与面试故事。

## 五、产品核心流程

```text
注册
  ↓
四步能力确认
（背景 / 能力 / 既有证据 / 完成确认）
  ↓
粘贴或选择目标 JD
  ↓
AI 分析职责、能力要求与个人差距
  ↓
知乎检索相关真实讨论，生成 3 个候选微项目主题
  ↓
选择 7 天或 14 天计划
  ↓
按任务执行并提交证据
  ↓
生成简历、作品集与 STAR 面试表达
```

## 六、当前产品能力

### 1. 个人能力画像

注册阶段通过四个独立界面完成能力确认：

- 背景：年级、专业、目标城市、每周可投入时间和目标方向；
- 能力：按岗位相关能力选择熟练程度、兴趣和掌握情况；
- 证据：记录课程、社团、项目、作品或其他已有经历；
- 完成：确认画像并进入 JD 分析。

只有完成完整能力确认后，用户才可以分析 JD 和创建微项目，确保后续推荐有明确的个人上下文。

### 2. JD 分析

用户可粘贴目标 JD。服务端优先使用结构化 AI 分析，提取岗位标题、职责、必备能力、优先能力、证据建议和下一步行动，并由服务端重新计算匹配分。

当模型未配置、请求超时、触发限流或返回不符合结构时，系统使用规则引擎回退，保证核心流程仍可用，并向用户明确当前分析来源。

### 3. 知乎驱动的选题

系统根据 JD 和能力缺口检索知乎相关讨论，返回 3 个候选选题供用户选择。每个主题包含问题背景、建议交付物、实践目标和知乎原始来源，用户可以打开原文核验上下文。

### 4. 微项目执行

支持 7 天和 14 天两种节奏。计划中记录任务状态、预计时间、交付物、验收标准、目标能力和知乎来源，适合在课余时间持续推进。

### 5. 证据与求职表达

证据页面引导用户填写“背景—任务—行动—结果—反思/下一步”，并标记草稿、待补事实和可用状态。表达页面将可用证据转换为：

- 简历项目描述；
- 作品集案例；
- STAR 面试故事。

## 七、知乎社区场景适配与价值

### 对知乎社区的适配

1. **问题导向**：知乎以问题、回答和经验讨论组织知识，天然适合作为微项目的问题池。JobProof 将用户从“浏览问题”引导到“选择一个问题并完成实践”。
2. **经验可信**：真实回答提供行业语境、常见方法和反例，帮助学生理解岗位能力在实际工作中的表现，而不是只看抽象技能名词。
3. **回到原文**：系统保存来源标题、链接和必要的短摘要，用户可回到知乎查看完整上下文，避免脱离原文的断章取义。
4. **鼓励高质量参与**：完成项目后，用户可以基于自己的实践形成更有事实支撑的观点或回答，促进“学习—实践—表达”的社区循环。
5. **不制造内容镜像**：产品不复制或长期保存知乎全文，不把社区内容包装成用户自己的成果；知乎讨论只作为选题和研究素材。

### 对用户和社区的价值

- 对学生：降低从 JD 到作品的行动门槛，获得可验证、可复述的成长记录；
- 对知乎：让高质量问题和经验产生新的实践入口，延长内容从阅读到行动的价值链；
- 对招聘沟通：让“我会某项能力”变成有背景、过程、结果和反思的事实表达。

## 八、技术方案

### 总体架构

```text
Next.js Web
  ├─ 用户界面：能力确认、JD、计划、证据、表达、知乎内容
  ├─ API Routes：JD 分析、知乎选题、OAuth、关注与创作数据
  ├─ 领域服务：画像、计划、证据、表达和匹配分计算
  └─ 数据层：localStorage 演示模式 + Supabase 云端模式
```

### 前端与服务端

- Next.js 15 App Router + TypeScript；
- React 交互页面，能力确认、计划任务和证据表单均为独立可操作界面；
- 服务端 API Route 统一处理密钥、第三方请求和数据校验；
- Zod 对 AI 返回结果和用户输入做结构化校验；
- 未配置云端服务时保留 localStorage 演示流程，便于黑客松现场运行。

### AI 分析

- 采用 OpenAI-compatible 接口调用 DeepSeek Flash 模型；
- 支持通过 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` 配置模型；
- 采用 JSON 结构化输出和 Zod 校验；
- 对 JD 原文进行引用二次核验，降低模型臆造职责和能力的风险；
- 邮箱、手机号、身份证号等敏感信息在发送给模型前脱敏；
- AI 不直接决定最终匹配分，分数由服务端依据能力权重计算。

### 知乎接入

当前已实现的服务端能力包括：

```text
POST /api/zhihu/project-context
GET  /api/zhihu/hot
GET  /api/zhihu/followees
GET  /api/zhihu/contents
GET  /api/auth/login
GET  /api/auth/callback
```

知乎 OAuth 使用授权码模式：用户授权后由服务端交换令牌，再调用授权范围内的接口。知乎 Access Secret 仅用于服务端检索能力，不进入浏览器、日志或 Git；OAuth 用户令牌用于用户主动授权后的账号信息和相关数据访问。

### 云端数据与安全

- Supabase 用于用户画像、能力项和后续云端数据持久化；
- 通过 SSR 客户端和服务端 API 访问数据库；
- `profiles`、`profile_competencies` 等表启用 Row Level Security，用户只能访问自己的数据；
- 密钥通过部署平台环境变量注入，不写入前端代码；
- 第三方内容采取最小化保存原则，仅保留完成选题和展示来源所需的元数据；
- 所有外部链接保留原始来源，方便用户核验和纠错。

## 九、可信度、隐私与合规设计

JobProof 的核心原则是“AI 辅助拆解，用户成果作为证据”。因此：

- AI 生成的建议必须经过用户确认，不能自动冒充用户经历；
- 证据字段区分事实、待补信息和可用状态，避免把推测写成结果；
- 用户可删除或修改自己的画像、计划和证据；
- 知乎数据只在授权和开放接口范围内使用，不进行网页抓取或内容镜像；
- Access Secret、OAuth App Key、数据库密钥等敏感配置只保存在服务端环境变量；
- 公网部署时应在隐私政策中说明数据用途、保存期限、第三方服务和用户删除方式。

## 十、项目创新点与可行性

### 创新点

1. **把求职准备变成短周期交付**：从“学习清单”升级为有验收标准的微项目。
2. **把知乎内容变成行动入口**：从阅读真实讨论开始，而不是凭空生成练习题。
3. **把能力确认、证据和表达连成闭环**：同一份事实材料同时服务于复盘、简历、作品集和面试。
4. **AI 有边界**：模型负责提取、解释和起草，匹配分和证据可信度由规则与用户确认共同约束。
5. **渐进式云端化**：本地演示模式保证可用，Supabase 提供可扩展的多用户数据基础。

### 可行性

- 核心流程已在公网 MVP 中可演示；
- AI、知乎和 Supabase 均通过独立服务端接口接入，便于替换和测试；
- 7/14 天计划的任务模型足够小，适合黑客松现场展示完整闭环；
- 后续可扩展更多岗位模板、团队协作、成果公开页和招聘方查看模式。

## 十一、黑客松现场演示脚本

1. 以学生身份注册，完成四步能力确认；
2. 粘贴一份产品/运营实习 JD；
3. 查看 AI 提取的岗位能力与个人差距；
4. 打开知乎候选讨论，展示 3 个真实选题及原始来源；
5. 选择 7 天计划，查看任务、交付物和验收标准；
6. 提交一条证据，展示完整度检查；
7. 生成简历、作品集和 STAR 面试表达；
8. 回到来源链接，说明知乎内容、用户成果和 AI 建议之间的边界。

## 十三、风险与应对

| 风险 | 应对方式 |
| --- | --- |
| AI 误解 JD 或编造建议 | 结构化输出、原文引用核验、规则回退、服务端计算匹配分 |
| 知乎接口权限或额度变化 | 统一封装知乎服务、展示降级状态、保留自定义主题入口 |
| 用户提交敏感信息 | 请求前脱敏、服务端密钥隔离、最小化保存 |
| 证据被包装成虚假经历 | 强制区分事实与待补项，表达内容回链用户证据 |
| 公网部署配置错误 | 环境变量校验、无密钥时可用的演示模式、生产构建和运行时检查 |

# JobProof 后续迭代方案

本文档承接 v0.1 MVP，说明 JobProof 从核心闭环、云端数据、结构化 AI 到小规模用户验证的分阶段迭代路径。

## 1. 迭代原则

- 先验证“JD → 微项目 → 证据 → 求职表达”的核心价值，再增加账号、云端和模型能力。
- 每个版本只引入一个主要变量，确保能够判断功能是否真正改善用户结果。
- 所有岗位结论保留 JD 原文依据，所有求职表达只使用用户提交的真实证据。
- 模型能力必须可校验、可追溯、可降级，不能成为核心流程的单点故障。
- 在进入下一阶段前，先完成当前阶段的验收标准。

## 2. 版本总览

| 版本 | 核心目标 | 关键结果 |
| --- | --- | --- |
| v0.2 | 完成核心闭环并接入知乎 OAuth | 用户能从一份 JD 做完项目，并用授权知乎数据辅助完善画像 |
| v0.3 | 引入 JobProof 真实账号与云端数据 | 支持真实用户、多设备同步和数据隔离 |
| v0.4 | 引入结构化 AI | 提升解析和计划个性化，同时保持可追溯和可降级 |
| v0.5 | 小规模用户验证 | 用 10–20 位目标用户验证完成率和求职表达价值 |

## 3. v0.2：完成“JD → 微项目 → 证据”闭环

### 目标

用户提交一份 JD 后，能够创建真正关联该 JD 的计划、完成任务、提交证据，并把证据转化为可使用的求职表达。用户也可以主动通过知乎 OAuth 登录，让公开创作和关注数据作为人物画像参考，而不是替代用户自述。

### P0 功能

1. **能力等级标准化**
   - 定义 0–3 级能力标准。
   - 区分自评能力、证据等级和岗位要求等级。
   - 为每个等级提供可理解的行为描述。

2. **完整匹配分和分项解释**
   - 展示能力匹配度、证据完备度和综合准备度。
   - 岗位必须项、核心项和加分项使用不同权重。
   - 每一项匹配结果保留 JD 原文、计算依据和缺口说明。

3. **基于缺口动态生成 7/14 天项目**
   - 根据最高优先级能力缺口选择项目模板。
   - 综合用户每周可投入时间、现有经验和目标岗位调整任务。
   - 每项任务必须包含行动、交付物和验收标准。

4. **任务状态、进度和本地持久化**
   - 支持待开始、进行中、已完成和待补充状态。
   - 自动计算计划进度。
   - 刷新或重新打开页面后仍能恢复 JD、计划和任务状态。

5. **证据工作台**
   - 支持提交文字、链接、成果说明、结果数字和反思。
   - 每份证据关联具体任务、能力和原始 JD。
   - MVP 阶段文件可先保存元数据或本地引用，不上传云端。

6. **证据完整度检查**
   - 检查背景、行动、结果、数字和反思五项。
   - 明确显示缺失字段，不对作品质量做虚假判断。
   - 不完整证据允许保存，但生成求职表达时标记待补充信息。

7. **从证据生成三种求职表达**
   - 生成 2–3 条简历 bullet。
   - 生成结构化作品集案例。
   - 生成 STAR 面试故事和追问卡。
   - 所有内容提供来源证据回链并允许用户编辑。

8. **知乎 OAuth 登录与用户入口**
   - 使用 Authorization Code Flow，服务端完成授权码换 Token 和用户基础信息读取。
   - 右上角展示已授权用户头像和昵称；点击后进入知乎用户中心。
   - 用户中心展示基础信息、公开创作列表和关注的人，列表使用知乎返回的 `NextOffset` 分页。
   - OAuth Token、App Key 和开放平台 Access Secret 只保存在服务端；浏览器只持有应用会话标识。
   - 登录、退出、Token 失效和用户取消授权均提供明确状态，不静默切换到其他账号。

9. **知乎数据画像参考**
   - 在用户明确授权并同意画像分析后，读取完成任务所需的最小数据范围。
   - 优先使用公开创作的标题、摘要、内容类型、时间和互动数据，以及公开关注列表。
   - 这些数据只能作为兴趣、主题偏好、表达方式和可能的职业方向参考，不能称为完整“知乎使用历史”。
   - 当前开放接口未提供用户完整浏览轨迹；不得从公开数据推断心理健康、政治立场、性取向、收入、人格诊断等敏感属性。
   - 画像中的每条 AI 结论必须标注“AI 参考”、数据来源、时间范围和置信度，并允许用户修改、隐藏或锁定。

### 数据策略

v0.2 暂不建立 JobProof 自有账号和云端数据库，继续使用 localStorage 保存核心业务数据；知乎 OAuth 仅作为外部授权入口，OAuth Token 保存在服务端短期会话中。为后续迁移预留稳定的数据版本号和 ID，避免 v0.3 无法识别旧数据。

#### 知乎行为数据口径

这里的“知乎使用历史”仅指用户主动授权后可读取的公开行为摘要，不代表完整浏览历史。v0.2 只使用以下数据：

| 数据来源 | v0.2 用途 | 约束 |
| --- | --- | --- |
| 公开创作的标题、摘要、类型和时间 | 判断长期兴趣主题与表达偏好 | 只能生成“可能感兴趣”的参考，不直接认定能力 |
| 公开关注的人及其主题 | 补充关注领域和职业方向线索 | 单一关注行为不能作为稳定结论 |
| 知乎用户基础信息 | 展示用户中心 | 不参与能力评分，不推断敏感属性 |
| 用户问卷、自评和主动提交的项目证据 | 形成正式画像与能力事实 | 用户明确填写和提交的内容优先级最高 |

画像分析必须单独取得用户同意，与“使用知乎登录”分开记录。用户拒绝画像分析、撤回授权或接口不可用时，直接使用问卷结果完成 JobProof 核心流程。

### 画像融合方案

画像不是一次性让 AI“猜一个人”，而是按能力、兴趣、岗位偏好和工作方式等维度分别计算。问卷是用户主动表达，优先级高于从知乎数据得到的推断。

#### 默认权重

在问卷完整、且授权知乎数据达到最小样本量时，采用：

```text
最终画像分 = 问卷结果 × 70% + 知乎数据 AI 参考 × 30%
```

推荐原因：

- 问卷是用户对自己的直接陈述，应作为主依据。
- 知乎数据可以补充用户没有意识到的主题偏好和表达习惯，但存在选择性使用和误判风险。
- AI 不能因为用户关注过某个主题，就把该主题认定为职业能力或稳定人格特征。

#### 动态权重

知乎参考权重根据数据量、时效性和信号一致性动态调整：

```text
AI 参考权重 = 30% × 数据置信度 × 新鲜度系数
问卷权重 = 1 - AI 参考权重
```

约束条件：

- 冷启动或未授权知乎：AI 参考权重为 `0%`，完全使用问卷。
- 只有少量或单一类型数据：AI 参考权重最高为 `15%`。
- 至少有 5 条公开创作或 10 个以上关注主题，且信号跨时间一致：AI 参考权重最高为 `30%`。
- 用户明确修改或锁定某项画像后，该项以用户结果为 `100%`，AI 只能提供旁注，不得覆盖。
- 问卷与 AI 结论冲突时，展示差异并询问用户，不自动折中成一个看似精确的结论。

#### 影响范围与覆盖规则

70/30 是完整问卷和足量数据下的默认上限，不是 AI 对所有字段的固定控制权。v0.2 按画像维度独立计算：

- 兴趣主题和表达偏好：允许使用问卷 `70%` + 知乎 AI 参考 `30%` 的默认比例。
- 岗位方向：问卷 `70%` + 知乎 AI 参考 `30%`，且必须结合当前 JD，不能仅凭知乎行为推荐岗位。
- 能力等级与能力证据：问卷和知乎 AI 参考均不能替代用户提交的项目、成果、数据或链接；知乎内容只能作为待验证的训练方向。
- 用户修改、确认或锁定某一项后，该项用户结果权重为 `100%`，AI 只能保留为可关闭的旁注。
- AI 参考必须展示来源、时间范围、置信度和影响权重；用户可以逐条确认、修改、隐藏或删除。

示例：用户问卷将“产品分析”评为高兴趣，知乎公开创作中也持续出现竞品和用户研究主题，则该方向可按 `70% + 30%` 形成“建议探索”结论；若问卷明确表示不考虑产品岗位，则最终岗位方向以用户选择为准，AI 不得覆盖。

#### 信号与画像维度

| 画像维度 | 可用信号 | 处理方式 |
| --- | --- | --- |
| 兴趣主题 | 创作标题、摘要、关注主题 | 主题聚类，输出“可能感兴趣”而非事实断言 |
| 表达偏好 | 创作内容类型、标题结构、摘要长度 | 仅作为内容生产方式参考 |
| 岗位方向 | 与产品、运营、研究、内容等主题的长期关联 | 结合问卷和 JD，不单独推荐岗位 |
| 能力证据 | 用户主动提交的项目和成果 | 只有用户证据可以进入能力事实层 |
| 工作方式 | 问卷、项目完成行为 | 知乎公开数据不直接推断人格和工作风格 |

#### 画像对象示例

```ts
interface ProfileSignal {
  dimension: "interest" | "expression" | "role_preference";
  statement: string;
  source: "questionnaire" | "zhihu_ai_reference";
  sourceIds: string[];
  confidence: number;
  observedAt: string;
  status: "suggested" | "confirmed" | "dismissed" | "locked";
}
```

只有 `confirmed` 或 `locked` 的画像信号可以影响微项目推荐；`suggested` 只能作为待确认提示。

### OAuth 与画像处理流程

```text
用户点击知乎登录
  → 服务端生成 state 并发起授权
  → 回调校验 state
  → 服务端换取 OAuth Token
  → 获取基础用户信息
  → 用户单独同意“使用创作/关注数据作为画像参考”
  → 拉取最小分页数据
  → 清洗、主题聚类、生成带来源的 AI 参考
  → 与问卷按动态权重合并
  → 用户确认、修改或锁定画像
```

登录同意不自动等于画像分析同意。用户可以只登录查看个人信息，也可以拒绝画像分析；拒绝后仍可使用 JD 分析和微项目功能。

### v0.2 实施顺序

1. 完成知乎 OAuth 授权、`state` 校验、服务端会话和退出登录。
2. 在右上角展示头像和昵称，用户中心展示基础信息、公开创作和关注列表，并使用接口返回的 `NextOffset` 加载更多。
3. 增加独立的“允许使用知乎公开行为生成画像参考”确认步骤，保存授权状态、数据时间范围和来源标识。
4. 先以规则聚类生成可解释的兴趣与表达信号，再按数据量、时效性和一致性计算 AI 参考权重。
5. 将问卷结果与 AI 参考按维度合并，展示冲突和来源，等待用户确认后再影响微项目推荐。
6. 用 Mock 数据覆盖未授权、少量数据、足量数据、冲突、撤回授权和用户锁定六种情形。

### 验收标准

- 使用一份产品或运营 JD，可完成从分析到表达生成的完整演示。
- 用户可完成知乎登录，右上角显示头像和昵称，用户中心可查看基础信息。
- 在 Mock 数据下可验证创作和关注列表分页、画像来源展示、冲突处理和用户锁定。
- 未授权知乎或知乎接口不可用时，问卷画像和 JobProof 核心流程仍可独立运行。
- AI 画像参考不会覆盖用户明确填写或锁定的结果。
- 每个计划都能追溯到对应 JD 和能力缺口。
- 刷新页面后任务状态和证据不丢失。
- 没有证据时不得生成带有虚构事实或数字的求职表达。
- 至少覆盖用户访谈、竞品分析、数据整理和内容策划四类项目模板。

### 暂不做

- JobProof 自有登录注册与跨设备同步。
- 公开作品集分享。
- 模型自动评价作品优劣。
- 全网岗位聚合与自动投递。
- 获取或推断用户完整浏览历史、敏感属性和未授权数据。

## 4. v0.3：真实账号与云端数据

### 目标

支持真实测试用户、多设备同步和严格的数据隔离，为持续使用和后续用户研究提供基础。v0.2 的知乎 OAuth 能力继续保留，但 OAuth Token、画像信号和 JobProof 业务数据统一迁移到按用户隔离的云端存储。

### 功能范围

- Supabase 邮箱魔法链接登录。
- PostgreSQL 数据表和 Row Level Security。
- 将 localStorage 数据迁移到用户账号。
- 将 v0.2 的知乎授权关联到 JobProof 用户，并支持解绑和重新授权。
- 画像信号保存来源、权重、版本、确认状态和删除记录。
- 私有文件上传与受控访问。
- 用户数据导出和删除。
- 基础异常监控与迁移失败恢复。

### 关键技术任务

- 建立 users、jobs、competencies、plans、tasks、evidence 和 expressions 数据表。
- 所有用户数据表启用 RLS，并为读写操作增加 owner policy。
- 本地迁移使用幂等导入，避免重复创建计划和证据。
- 成果文件默认私有，通过短期签名 URL 访问。
- 密钥只保存在服务端环境变量中。

### 验收标准

- 用户可以通过邮箱登录并在两台设备看到一致数据。
- 不同用户之间无法读取或修改对方的数据与文件。
- v0.2 本地数据可以由用户确认后一键迁移，失败时不删除本地副本。
- 用户可以导出并删除自己的全部云端数据。

## 5. v0.4：结构化 AI

### 目标

使用模型提升 JD 解析准确性和计划个性化，同时保持结果可追溯、可验证、可降级。

### 功能范围

- LLM Provider Adapter。
- JD Structured Output。
- Prompt 版本管理。
- Schema 校验和一次自动重试。
- 模型不可用时回退规则引擎。
- 建立 20 份人工标注 JD 回归集。

### 处理管线

```text
JD 清洗
  → 敏感信息过滤
  → 结构化能力抽取
  → Schema 校验
  → 失败时修复并重试一次
  → 仍失败则回退规则引擎
  → 保存模型、Prompt 和 Schema 版本
```

### 输出约束

- 每项能力必须附带 JD 原文证据和提取置信度。
- 模型不得补写用户没有提交的经历、结果和数字。
- 计划必须符合用户可投入时间并给出可验收交付物。
- 所有模型输出在保存前允许用户确认和编辑。

### 回归集指标

- 核心能力识别准确率。
- 必须项与加分项分类准确率。
- JD 原文引用正确率。
- Schema 首次通过率和重试通过率。
- 规则引擎回退成功率。

### 验收标准

- 20 份标注 JD 的核心能力识别结果达到团队约定基线。
- 无效模型输出不能进入正式数据。
- 模型调用失败时用户仍能完成基础分析和计划创建。
- 每条 AI 结果可以定位到模型版本、Prompt 版本和输入来源。

## 6. v0.5：小规模用户验证

### 目标

邀请 10–20 位准备产品或运营岗位的大学生完成一轮真实任务，验证产品是否真正促进项目完成和证据产出。

### 功能范围

- 匿名行为埋点。
- 页面内用户反馈入口。
- 项目完成率和证据导出率看板。
- 根据反馈优化能力包和任务模板。
- 招募、同意说明和访谈记录流程。

### 核心漏斗

```text
进入产品
  → 提交 JD
  → 完成能力分析
  → 创建微项目
  → 完成至少一项任务
  → 提交证据
  → 导出求职表达
```

### 建议指标

- JD 分析完成率 ≥ 70%。
- 微项目创建率 ≥ 50%。
- 至少一项任务完成率 ≥ 40%。
- 7/14 天项目完成率 ≥ 30%。
- 证据提交用户中的求职表达导出率 ≥ 60%。
- “我知道下一步做什么”的用户评分 ≥ 4/5。

### 验收标准

- 完成 10–20 位目标用户的完整测试记录。
- 能区分用户在哪个漏斗环节流失。
- 汇总至少 5 个重复出现的问题或需求。
- 基于数据确定下一版本继续、调整或停止的功能。
- 形成一份用户验证报告和一份任务模板改进清单。

## 7. 阶段依赖与发布条件

- v0.3 依赖 v0.2 的数据结构稳定，否则本地数据迁移成本会快速上升。
- v0.3 依赖 v0.2 明确区分“登录授权”“画像分析授权”和“用户确认画像”三种状态。
- v0.4 依赖 v0.2 的规则引擎保留为降级路径，不能直接删除。
- v0.5 依赖 v0.3 的账号隔离和数据删除能力，以支持真实用户测试。
- 每次发布前必须完成类型检查、构建验证、关键流程手测和敏感信息扫描。
- 未达到当前版本验收标准时，不因版本号计划而提前进入下一阶段。

## 8. 当前优先事项

v0.1 发布后立即进入 v0.2。第一开发顺序建议为：

1. 固化能力、证据和岗位要求的等级模型。
2. 重构匹配算法并补充边界测试。
3. 建立 JD、计划、任务和证据之间的关联数据结构。
4. 实现动态 7/14 天计划与任务状态持久化。
5. 实现证据工作台和完整度检查。
6. 实现三种求职表达及来源回链。
7. 完成一条端到端演示用例并发布 v0.2。

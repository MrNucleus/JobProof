# JobProof v0.5：结构化 AI JD 分析

## 本版目标

在现有规则分析的基础上，接入一个可替换的 LLM Provider，让模型负责从 JD 中抽取岗位能力，同时保留确定性的匹配计算和规则降级路径。

## 当前流程

```text
用户提交 JD + 已确认能力画像
  → 服务端脱敏
  → LLM 结构化抽取（可选）
  → 校验能力 key 和 JD 原文引用
  → 服务端计算匹配分
  → AI 成功：展示 AI 结构化分析
  → AI 未配置/失败：回退规则引擎并继续流程
```

## 配置

服务端环境变量：

```env
LLM_API_KEY=你的DeepSeek API Key
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash
```

`LLM_API_KEY` 不使用 `NEXT_PUBLIC_` 前缀，不写入源码、日志或 Git。未配置时不影响产品使用，JD 继续由规则引擎分析。

当前默认使用 DeepSeek Flash（V4 Flash 系列）。DeepSeek 官方当前推荐模型名为 `deepseek-flash`；`deepseek-v4-flash` 是旧名称，对应模型已退休，不建议用于新部署。如需测试兼容名称，可通过 `LLM_MODEL` 覆盖默认值。

## 可信度边界

- 模型只能选择产品/运营能力包中的 8 个能力 key。
- 每项能力必须返回 JD 原文引用，服务端会再次核验引用是否出现在 JD 中。
- 引用无法核验、结构化输出不合法或请求失败时，整次分析回退到规则引擎。
- 匹配分仍由 `calculateMatch` 在服务端计算，模型不能直接决定分数。
- JD 中的邮箱、手机号和身份证号在发送给模型前脱敏。
- 页面显示“AI 结构化分析”或“规则引擎分析”，并提示是否发生降级。

## API 行为

`POST /api/jobs/analyze` 的返回新增：

- `analysisMode`: `ai` 或 `rules`
- `analysisNotice`: 可选的降级或核验提示
- `analysisModel`: 成功使用的模型名称

## 故障处理

- 没有 `LLM_API_KEY`：直接使用规则分析。
- AI 超时、限流、鉴权失败：返回规则分析，不阻塞用户。
- AI JSON 不符合 Schema：自动重试一次，仍失败则回退规则分析。
- 规则分析本身继续沿用现有输入校验、请求体大小限制和频率限制。

## 本版未做

- 不让模型直接生成微项目任务；现有任务模板继续负责可执行性。
- 不把完整 JD 或用户画像写入日志。
- 不自动选择具体模型供应商；通过 OpenAI-compatible `base_url` 保留替换空间。

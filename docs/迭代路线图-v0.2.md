# JobProof v0.2 产品与技术迭代路线图

状态：设计草案，待确认后按模块编码

## 1. 当前版本盘点

v0.1 已跑通可演示骨架：

- 四步个人能力确认；
- 个人中心；
- JD 文本输入和本地规则分析；
- 静态 7 天微项目；
- 浏览器本地保存能力画像与最近一次 JD 分析。

当前仍是演示版，主要缺口：

- 能力等级缺少统一、可验证的行为标准；
- JD 匹配只计算能力和证据，尚未完整纳入兴趣与硬约束；
- 微项目与 JD 缺口没有动态关联；
- 用户不能真正保存任务进度、提交成果和生成求职表达；
- 数据只保存在浏览器，尚无账号、多设备同步和权限控制；
- `storage.ts` 与 `storage.complete.ts` 存在临时重复，需要收敛为统一 Repository。

## 2. 产品北极星

JobProof 的核心不是“分析得有多聪明”，而是：

> 用户是否完成了一份能证明目标岗位能力的真实成果。

北极星指标：**每周新增“已验证能力证据”的用户数**。

配套漏斗：

```text
完成能力画像
  → 分析/选择 JD
  → 创建微项目
  → 提交第一份证据
  → 证据达到可用标准
  → 导出求职表达
```

## 4. 分阶段迭代

### v0.2：完成“JD → 微项目 → 证据”闭环

目标：用户提交一份 JD 后，能创建真正关联该 JD 的计划、完成任务并提交证据。

P0 功能：

1. 能力等级标准化；
2. 完整匹配分和分项解释；
3. 基于缺口动态生成 7/14 天项目；
4. 任务状态、进度和本地持久化；
5. 证据工作台；
6. 证据完整度检查；
7. 从证据生成三种求职表达。

暂不接账号系统，继续用本地数据验证核心闭环。

### v0.3：真实账号与云端数据

目标：支持真实测试用户、多设备同步和数据隔离。

- Supabase 邮箱魔法链接；
- PostgreSQL 数据表和 Row Level Security；
- 本地数据迁移到账号；
- 私有文件上传；
- 用户数据导出和删除。

### v0.4：结构化 AI

目标：用模型提升 JD 解析和计划个性化，同时保持可追溯、可降级。

- LLM Provider Adapter；
- JD Structured Output；
- Prompt 版本管理；
- Schema 校验和一次重试；
- 模型不可用时回退规则引擎；
- 20 份人工标注 JD 回归集。

### v0.5：小规模用户验证

目标：邀请 10–20 位产品/运营求职学生完成一轮真实任务。

- 匿名行为埋点；
- 用户反馈入口；
- 项目完成率和证据导出率看板；
- 根据反馈优化能力包和任务模板。

## 5. v0.2 产品详细设计

### 5.1 能力等级行为标准

能力分数不能只靠用户主观理解。每项能力使用统一四级框架，并为具体能力提供例子：

| 等级 | 通用定义 | 用户访谈示例 |
|---:|---|---|
| 0 | 不了解方法，也未实践 | 不知道如何设计访谈问题 |
| 1 | 了解方法，在指导下做过 | 跟随模板旁听或完成 1 次访谈 |
| 2 | 能独立完成一个小任务 | 独立访谈 3–5 人并整理发现 |
| 3 | 能交付完整结果并解释决策 | 设计研究、归纳需求、输出优先级建议并复盘 |

产品要求：能力自评页点击“怎么看等级”时显示行为例子；不能只显示抽象标签。

### 5.2 匹配结果结构

匹配结果拆为四项，不只显示总分：

| 分项 | 权重 | 解释 |
|---|---:|---|
| 能力覆盖 | 45% | 必备能力达到等级 2 的比例 |
| 证据强度 | 25% | 能力是否有可说明的事实证据 |
| 兴趣偏好 | 15% | 是否愿意持续完成岗位核心任务 |
| 硬性约束 | 15% | 年级、城市、可投入时间是否满足 |

总分旁必须显示置信度：

- 高：能力和证据填写完整，JD 要求明确；
- 中：部分能力或约束未知；
- 低：JD 过短、能力画像缺失或规则未覆盖。

### 5.3 计划生成

用户选择：

- 重点补强能力；
- 7 天或 14 天；
- 每周投入时间；
- 项目主题偏好。

生成结果必须包含：

- 项目目标；
- 每项任务预计用时；
- 交付物；
- 验收标准；
- 对应 JD 原文；
- 完成后可以证明的能力。

任务总预计用时不得超过用户输入的时间预算。

### 5.4 证据工作台

每个任务支持：

- 文字说明；
- 外部成果链接；
- 结果数字；
- 反思；
- 文件上传预留（v0.3 开启）。

证据完整度由五项组成，每项 20 分：背景、个人任务、具体动作、结果、反思。

完整度只表示“信息是否齐全”，不表示作品质量，避免虚假的 AI 权威感。

### 5.5 求职表达

一份证据可以生成：

- 简历：一至两条 bullet；
- 作品集：背景、问题、过程、结果、反思；
- 面试：STAR 故事和三个事实核验问题。

任何缺失事实以“待补充”呈现；用户确认前均为草稿。

## 6. v0.2 技术模块

### 6.1 Domain Schema

建立统一的 Zod Schema：

- `UserProfileSchema`
- `CompetencyProfileSchema`
- `JobSchema`
- `JobAnalysisSchema`
- `MatchResultSchema`
- `PlanSchema`
- `TaskSchema`
- `EvidenceSchema`
- `ExpressionSchema`

TypeScript 类型从 Schema 推导，避免 API、页面和存储使用不同类型。

### 6.2 Repository 层

```ts
interface ProfileRepository {
  get(): Promise<UserProfile | null>;
  save(profile: UserProfile): Promise<void>;
}

interface PlanRepository {
  list(): Promise<Plan[]>;
  get(id: string): Promise<Plan | null>;
  save(plan: Plan): Promise<void>;
}
```

v0.2 使用 `LocalStorageRepository`，v0.3 替换为 `SupabaseRepository`。页面不直接调用 `localStorage`。

### 6.3 Service 层

- `ProfileService`：完成度、能力状态和画像摘要；
- `JobAnalysisService`：规则抽取、引用定位和置信度；
- `MatchingService`：确定性计算四项匹配分；
- `PlanService`：按缺口、时间预算和模板生成计划；
- `EvidenceService`：完整度计算和状态流转；
- `ExpressionService`：基于证据生成三种草稿。

### 6.4 分析器接口

```ts
interface JobAnalyzer {
  analyze(input: AnalyzeJobInput): Promise<JobAnalysis>;
}
```

- `RuleBasedJobAnalyzer`：v0.2 默认实现；
- `LlmJobAnalyzer`：v0.4 实现；
- `FallbackJobAnalyzer`：AI 失败时自动使用规则分析。

### 6.5 ID 与数据版本

- 使用 `crypto.randomUUID()` 生成实体 ID；
- localStorage key 统一为 `jobproof.v2.*`；
- 所有本地数据带 `schemaVersion: 2`；
- 提供 v1 → v2 迁移函数，保护现有测试数据。

## 7. v0.2 验收场景

### 场景 A：已有目标 JD

1. 用户完成能力确认；
2. 粘贴一份产品运营 JD；
3. 获得四项匹配分、置信度、原文引用；
4. 选择一个缺口创建 7 天计划；
5. 刷新页面后计划仍存在；
6. 完成任务并提交一份证据；
7. 生成三种求职表达。

### 场景 B：事实不足

1. 用户把能力自评为等级 2，但没有填写证据；
2. 系统将该能力标记为“会做、待验证”；
3. 匹配时能力分计入、证据分不计入；
4. 系统推荐验证任务，不指责用户“能力不足”。

### 场景 C：JD 过短

1. 用户输入信息不足的 JD；
2. 系统显示低置信度；
3. 不生成貌似精确的高匹配分；
4. 引导用户补充完整职责和要求。

## 8. 开发顺序

每个模块单独提交，便于 GitHub 审核：

1. `refactor: add domain schemas and repository layer`
2. `feat: improve competency behavior anchors`
3. `feat: add explainable job matching breakdown`
4. `feat: generate persistent gap-based plans`
5. `feat: add evidence workspace and completeness check`
6. `feat: generate traceable career expressions`
7. `test: cover core JobProof user journey`

## 9. 当前建议

下一步先做 **技术基础模块：Domain Schema + Repository + v1 数据迁移**。

原因：后续的任务进度、证据、求职表达都会依赖统一数据模型。如果继续直接在页面内使用 localStorage，将产生更多重复和迁移成本。

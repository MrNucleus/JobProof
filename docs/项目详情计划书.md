# JobProof 项目详情计划书

版本：v0.2 规划版
项目名称：JobProof 能力证据工坊
项目定位：面向零实习或实习较少的大学生，把目标岗位 JD 转化为可完成、可验证、可展示的能力证据。
目标场景：大二、大三学生申请第一份产品或运营实习。

## 一、项目概述

JobProof 解决的是“知道岗位要求，但不知道如何证明自己具备能力”的求职问题。用户输入一份目标岗位 JD，系统提取岗位需要的能力，结合用户自评和已有经历识别能力缺口，再生成一个 7 天或 14 天的微项目。用户完成任务并提交成果后，系统把真实成果整理为简历 bullet、作品集案例和 STAR 面试故事。

产品核心链路：

```text
目标 JD
  → 能力拆解
  → 能力差距
  → 7/14 天微项目
  → 任务成果与证据
  → 简历、作品集、面试表达
```

知乎接入用于补充用户的公开兴趣和表达偏好参考。知乎数据不替代用户问卷，也不能直接作为职业能力证据。

## 二、项目目标

### 2.1 产品目标

1. 让用户在 15 分钟内理解一份 JD 的核心能力要求。
2. 让用户得到一个有时间限制、交付物和验收标准的微项目。
3. 让用户完成至少一项真实成果，并形成可编辑的求职表达。
4. 用知乎公开创作和关注数据辅助完善兴趣画像，同时保持数据来源透明、用户可控。

### 2.2 技术目标

1. 使用单体全栈架构完成前端、接口、数据处理和部署。
2. 所有岗位分析结果能追溯到 JD 原文。
3. 所有求职表达只能使用用户提交的事实，不生成虚构经历或数据。
4. OAuth 密钥、Access Secret 和用户 Token 只在服务端保存。
5. 模型或知乎接口不可用时，核心 JD 分析和任务流程仍能降级运行。

### 2.3 黑客松展示目标

在 3 分钟演示中完整展示：

```text
粘贴产品运营 JD
  → 查看能力卡和匹配解释
  → 创建 7 天微项目
  → 提交一份竞品分析成果
  → 生成简历、作品集和面试故事
  → 展示知乎登录与公开数据参考入口
```

## 三、目标用户与使用场景

| 用户类型 | 特征 | 主要需求 | JobProof 提供的结果 |
| --- | --- | --- | --- |
| 补强型学生 | 大二、大三，准备第一次投递 | 不知道岗位要求与自身差距 | 能力差距卡和微项目计划 |
| 转化型学生 | 有课程、社团或兼职经历 | 经历无法写成有效成果 | 证据整理和求职表达 |
| 探索型学生 | 尚未确定岗位方向 | 想了解适合尝试的方向 | 基于问卷和 JD 的探索建议 |

首版优先服务补强型学生，岗位范围聚焦产品和运营实习。

## 四、产品功能规划

### 4.1 用户画像与 onboarding

收集年级、专业、目标城市、每周可投入时间、求职阶段、目标岗位族和能力自评。能力记录区分三类信息：

- 自评等级：不了解、接触过、能独立完成小任务、能交付完整结果。
- 证据强度：暂无证据、课程作业、社团或兼职、个人项目、实习成果。
- 兴趣偏好：喜欢、可以尝试、不想做。

规则：没有用户证据的能力只能标记为“待验证”，不能展示为已掌握。

### 4.2 JD 分析

用户粘贴岗位 JD 后，系统输出：

- 岗位标题、公司、地点和工作摘要。
- 3–5 个核心能力单元。
- 必须项、核心项和加分项。
- 每项能力对应的 JD 原文。
- 用户已有证据、能力缺口和验证建议。

每张能力卡都必须显示原文依据和分析解释。

### 4.3 匹配算法

推荐岗位或 JD 分析结果使用可解释评分：

```text
综合匹配分 = 45% 能力覆盖度
           + 25% 证据强度
           + 15% 兴趣与岗位偏好
           + 15% 基本约束匹配
```

页面同时展示总分和分项分数。硬性条件不满足时显示风险，不用一个总分掩盖城市、年级或时间约束问题。

### 4.4 微项目计划

根据能力缺口、用户每周可投入时间和目标方向生成 7 天或 14 天计划。每项任务必须包含：

- 任务目标。
- 操作步骤。
- 输入模板或参考示例。
- 交付物。
- 数量、格式和质量验收标准。
- 关联的岗位能力和 JD 原文。

示例：产品运营实习生竞品分析项目。

| 任务 | 交付物 | 验收标准 |
| --- | --- | --- |
| 访谈用户 | 访谈记录表 | 至少 5 人，记录原始问题和关键原话 |
| 分析竞品 | 竞品对比表 | 至少 5 个竞品，覆盖 3 个统一指标 |
| 整理数据 | 指标摘要 | 明确数据来源、口径和时间范围 |
| 提出建议 | 结论页 | 至少 2 条建议，每条有依据和优先级 |
| 汇报复盘 | 90 秒讲解稿 | 说明背景、行动、结果和下一步 |

### 4.5 证据工作台

证据可以关联任务和能力，支持文字、链接、文件元数据、结果数字和反思。完整度检查包含：

1. 背景或问题。
2. 用户承担的任务。
3. 具体行动。
4. 结果或数字。
5. 反思与下一步。

缺少数字时允许保存，但必须显示“待补充”，不得自动编造结果。

### 4.6 求职表达

从已确认的证据生成三类草稿：

- 简历 bullet：动作、方法、工具和结果。
- 作品集案例：背景、过程、结果和反思。
- STAR 面试故事：情境、任务、行动、结果和追问卡。

每条表达显示来源证据，用户编辑确认后才作为正式版本。

### 4.7 知乎能力接入

已规划的知乎能力包括：

- OAuth 登录。
- 右上角头像和昵称展示。
- 用户中心的基础信息。
- 公开关注列表和公开创作列表。
- 知乎热榜展示。
- 使用知乎返回的分页游标加载更多。

画像分析需要单独取得用户同意。允许使用的参考信号包括公开创作标题、摘要、类型、时间和公开关注主题；不获取或推断完整浏览历史、搜索历史、心理健康、政治立场、性取向、收入等敏感信息。

画像融合默认规则：

```text
完整问卷下：最终画像 = 问卷结果 × 70% + 知乎 AI 参考 × 30%
少量数据下：知乎 AI 参考最高 15%
未授权知乎：知乎 AI 参考为 0%
用户锁定字段：用户结果为 100%
```

知乎参考必须标注来源、时间范围、置信度和“AI 参考”状态。它可以影响兴趣和岗位探索建议，不能直接把知乎内容变成能力证据。

## 五、页面与用户流程

### 5.1 页面清单

| 页面 | 主要内容 | 优先级 |
| --- | --- | --- |
| `/` | 产品入口和核心价值 | P0 |
| `/onboarding` | 背景与能力确认 | P0 |

| `/zhihu-hot` | 知乎热榜 | P1 |
| `/account` | 知乎用户信息、关注和创作 | P1 |
| `/evidence` | 证据提交和完整度 | P0 |
| `/expressions` | 三种求职表达 | P0 |

### 5.2 核心用户旅程

```text
填写背景
  → 完成能力自评
  → 粘贴目标 JD
  → 确认能力卡
  → 创建 7/14 天计划
  → 完成任务并提交证据
  → 检查证据完整度
  → 生成并编辑求职表达
```

知乎登录属于可选支线：

```text
点击知乎登录
  → 服务端生成 state
  → 用户授权
  → 服务端换取 Token
  → 创建应用会话
  → 展示用户中心
  → 用户单独同意画像分析
```

未登录知乎时，用户仍可完成 JobProof 的核心流程。

## 六、技术架构

### 6.1 技术栈

- Next.js App Router。
- React 与 TypeScript。
- Route Handlers 实现服务端接口。
- Zod 校验请求和结构化输出。
- localStorage 保存 v0.2 核心业务数据。
- Netlify Blobs 保存需要跨实例共享的会话数据。
- 后续使用 Supabase Auth、PostgreSQL 和 Storage。

### 6.2 模块划分

```text
app/
  页面、Route Handlers 和用户流程
components/
  页面组件和交互组件
lib/
  领域数据、存储、知乎客户端和会话
docs/
  产品、技术和迭代文档
```

核心接口：

```text
POST /api/jobs/analyze
GET  /api/zhihu/hot
GET  /api/zhihu/followees
GET  /api/zhihu/contents
GET  /api/auth/login
GET  /api/auth/callback
GET  /api/auth/me
POST /api/auth/logout
```

### 6.3 数据原则

1. JD 原文、能力分析、计划、任务、证据和表达之间保存关联 ID。
2. 生成内容保存来源证据和版本信息。
3. OAuth Token、App Key、Access Secret 不进入前端、URL、日志和 Git。
4. 用户成果默认私有，未来通过签名链接控制分享。
5. AI 失败时回退规则引擎，不能阻断核心流程。

## 七、分阶段排期

### 阶段 0：基础修复与线上可用性

周期：1–2 天。

任务：

- 确认 GitHub `main` 与 v0.2 Release 指向一致。
- 检查 Netlify 构建命令、发布目录和 Functions 配置。
- 修复公网首页 404。
- 验证首页、JD 分析接口和知乎接口在生产环境可访问。
- 在 Netlify 配置服务端环境变量和正确回调地址。

完成标准：公网首页可打开，生产部署显示正确提交，接口不返回静态站点 404。

### 阶段 1：v0.2 核心闭环

周期：3–5 天。

任务：

- 完善能力等级和匹配分解释。
- 完善 7/14 天动态计划。
- 接通任务状态、进度和本地持久化。
- 完成证据工作台和完整度检查。
- 生成简历、作品集和面试表达。
- 用一份产品运营 JD 完成端到端演示。

完成标准：用户可以从 JD 走到至少一份证据和三类求职表达。

### 阶段 2：知乎 OAuth 与公开数据

周期：2–4 天。

任务：

- 配置知乎 OAuth 回调和 state 校验。
- 完成头像、昵称和用户中心。
- 完成关注列表和创作列表分页。
- 完成热榜页面。
- 增加画像分析单独授权状态。
- 增加来源、置信度和用户确认状态展示。

完成标准：授权用户可登录、退出、查看公开信息；未授权或接口失败时 JobProof 核心流程仍正常。

### 阶段 3：v0.3 云端账号

周期：1–2 周。

任务：

- Supabase 邮箱魔法链接。
- PostgreSQL 用户、岗位、计划、任务、证据和表达表。
- RLS 数据隔离策略。
- localStorage 数据迁移。
- 私有文件上传和签名 URL。
- 用户数据导出、删除和解绑知乎。

完成标准：两个测试用户互相不可见数据，两台设备可以读取同一份数据。

### 阶段 4：v0.4 结构化 AI

周期：1–2 周。

任务：

- 实现 LLM Provider Adapter。
- 结构化 JD 抽取和 Schema 校验。
- Prompt 版本管理。
- 失败重试一次并回退规则引擎。
- 建立 20 份人工标注 JD 回归集。

完成标准：模型输出可校验、可追溯、可降级，不能生成无来源事实。

### 阶段 5：v0.5 小规模验证

周期：2–3 周。

任务：

- 邀请 10–20 位产品或运营求职学生。
- 增加匿名行为埋点和反馈入口。
- 统计 JD 分析完成率、计划创建率、任务完成率和证据导出率。
- 访谈用户并优化任务模板。

完成标准：完成一轮真实任务验证，并形成下一版本的改进清单。

## 八、GitHub 协作与发布流程

### 8.1 分支策略

```text
main                  生产稳定版本
feat/<功能名>          新功能开发
fix/<问题名>           缺陷修复
docs/<主题名>          文档更新
```

开发者从最新 `main` 创建功能分支，每个分支只处理一个主题。禁止直接在 `main` 上开发或提交密钥。

### 8.2 Pull Request 流程

1. 从 `main` 更新本地代码。
2. 创建功能分支并完成实现。
3. 运行 `npm run typecheck` 和 `npm run build`。
4. 提交 PR，说明问题、方案、测试结果和截图。
5. 至少一名协作者检查后合并。
6. 合并后删除已完成分支。

### 8.3 Release 流程

1. 确认 `main` 的生产构建通过。
2. 更新版本说明和变更记录。
3. 创建语义化版本标签，例如 `v0.2`、`v0.3`。
4. Release 说明包含新增功能、修复、已知限制和部署要求。
5. Netlify 生产部署完成后，核对部署提交与 Release 标签一致。

## 十、风险与应对

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| JD 内容格式不统一 | 分析结果不稳定 | 先清洗文本，保留原文引用，并提供人工编辑 |
| 用户高估能力 | 推荐计划失真 | 分离自评等级和证据等级 |
| AI 编造经历或数字 | 伤害求职可信度 | 只允许从证据生成，缺失字段显示待补充 |
| 知乎接口或 Token 失效 | 用户中心不可用 | 明确错误状态，核心流程回退到问卷 |
| OAuth 回调地址不一致 | 登录失败 | 统一使用生产 HTTPS 回调并在部署前联调 |
| Netlify 多实例会话不一致 | OAuth 回调丢失 | 使用共享 Blob、数据库或 Redis |
| 数据泄露 | 用户隐私风险 | 服务端保管密钥，成果默认私有，启用最小数据范围 |
| 功能范围扩张 | 延期 | 首版只聚焦产品/运营岗位和一条核心用户旅程 |
